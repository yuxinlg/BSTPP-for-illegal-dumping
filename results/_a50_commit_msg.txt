CI-10 -- A CONFIG-OWNED BOOLEAN ARGUMENT IS A bool, NEVER MERELY TRUTHY.
cox_background is documented `bool` and consumed as `if cox_background:` with
nothing checking it, so the accept set is every Python object and the branch is
taken by TRUTHINESS. This is CI-9's defect with the sign flipped: there a bad
value was accepted and IGNORED, here it is accepted and ACTED ON, in the
direction opposite to what it says. A user who writes cox_background='false'
gets a Gaussian-process background -- a different model with different
parameters -- and nothing reports a problem: model.args['model'] reads
'cox_hawkes' and is a perfectly well-formed record of a model they did not ask
for. Every figure downstream is then of the other model.
  THE SHIPPED DEFAULT IS PART OF THE DEFECT. It was the string 'cox', so the
  package's own default sat outside the type its own docstring declared, and a
  bool-only enforcement must move it. That is what makes this SC/API rather
  than a quiet tightening: the default's TYPE changes and its MEANING does not
  (both truthy, so the selected model is identical and no pinned value moves),
  and cox_background='cox' stops being accepted.
  WHY 'cox' IS NOT KEPT AS A LEGACY ALIAS. Keeping one string alive keeps the
  truthiness coercion alive with it, and the reader then has to remember which
  string is the good one -- while 'false', the string that motivates the whole
  row, differs from it only in spelling. OP-3/OP-4 settled this the other way
  round for standardize_cov: legacy values are rejected EXPLICITLY, never
  silently reinterpreted. The clause branches on the old default and appends
  "use cox_background=True for the same model", because the upgrading user hits
  'cox' first, having copied it out of the signature.
  np.bool_ IS ACCEPTED, and the reason is a CPython fact rather than a
  preference. D-42 accepts np.float64 because it IS a float subclass; bool
  CANNOT BE SUBCLASSED in CPython, so np.bool_ has no way to opt into the same
  treatment, and rejecting it would punish numpy for a language restriction.
  The check is on the SCALAR type, never on an array's truthiness -- bool(arr)
  on a multi-element array raises its own ValueError with the wrong message,
  the split identity D-40 forbids. 0 and 1 ARE rejected: D-42's
  bool-is-not-an-int boundary from the other side.

CAN CI-10 MAKE EITHER PIN-5 CONFIGURATION UNCONSTRUCTIBLE? MEASURED: NO.
A rejection clause is invisible to a value-and-gradient comparison over the
configurations that still construct -- if one stops constructing, pin_check_v2
raises and writes no record, so the comparison sees not a moved number but an
absent key, which before A-48 was counted as no diff.
_a50_constructibility_probe.py reads the cox_background actually passed at
every construction site in the harness BY AST rather than by rerunning it, and
puts each value through validate_cox_background. All six sites pass a bool:
cox_hawkes passes True (changed in this commit), the other four Hawkes_Model
sites pass False, and LGCP_Model has no such parameter and is reported NOT
APPLICABLE rather than omitted. BOTH PIN-5 LEGS pass cox_background=False, so
CI-10 cannot reject either, and the polygon regime reaches the construction
path and returns from it. NO SITE RELIES ON THE DEFAULT, so the default's type
change moves nothing in the harness. The gate line agrees by a second and
weaker route: the forward run reads compared=6/6 with baseline_only=[].
